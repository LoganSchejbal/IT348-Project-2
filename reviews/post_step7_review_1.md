| 1 | High | PLAN.md, "Post Step 7" section — `run_step1_load`, `run_step3_preprocess`, `run_step4_train` vs. `run_selected_step` / `format_dataframe_for_console` | The plan says `run_selected_step` prints "each result with `format_dataframe_for_console`", but `format_dataframe_for_console(df: pd.DataFrame) -> str` only accepts a single dataframe. `run_step1_load` is planned to return `dict[int, pd.DataFrame]` (one frame per year), `run_step4_train` returns `dict[str, object]` (fitted classifiers, not a frame), and `run_step3_preprocess` returns `None`. None of these three fit the one shared formatter, so `--step load`, `--step train`, or `--step preprocess` (and `--step all`, which runs every step) would hit a function that can't render its own step's output as currently specified. | Either (a) give each of these three steps its own small summary dataframe to return (e.g. rows/cols per year for load, hyperparameters per classifier for train, train/test shapes and years for preprocess) so the single formatter still works everywhere, or (b) have `run_selected_step` branch on return type/step name instead of assuming every step yields a `pd.DataFrame`. Worth deciding before implementation since it affects three of the seven step functions' signatures. |
| 2 | Medium | PLAN.md, "Post Step 7" section — `build_arg_parser` / `ensure_data_loaded` | The plan doesn't say what happens when `--data-dir` points to a missing or empty directory. Since this driver is explicitly meant to be something "a grader or the live check-in can actually run from the console," an unhandled exception bubbling up from deep in `data_loader.py` (if it doesn't already validate this) would be a poor console experience and AGENTS.md's conventions call for documented, understandable failure paths. | Add a line to the plan that `ensure_data_loaded` (or `main`) checks `data_dir.exists()`/non-empty before calling `load_all_years`, and raises a clear, actionable error (or confirm `discover_dataset_files` already does this and cite it) rather than leaving it unspecified. |
| 3 | Low | src/sustainable.py, `compare_static_vs_retrained` (the `if len(merged) != len(static_df): raise ValueError(...)` block after the `pd.merge(..., validate="one_to_one")` call) | This check is unreachable as written: the function already requires `static_keys == retrained_keys` before merging, and `validate="one_to_one"` itself guarantees no duplicate keys on either side. Given both, `len(merged)` can never differ from `len(static_df)`. It's not harmful, but it reads as if it catches a case the two checks above it don't already rule out. | Either drop the redundant check, or change the comment to make clear it is a defensive/belt-and-suspenders assertion rather than a check for a distinct failure mode. |
| 4 | Low | src/sustainable.py, `static_model_trajectory` (`train_years: list[int] \| None = None`) | The leakage guard this function's docstring advertises ("the same leakage guard the Step 6 baseline uses, now exercised here too") only fires if the caller remembers to pass `train_years`; the default is `None`, which skips it. The only current caller (`run_sustainability_comparison`) does pass it, so there's no live bug today, but this module exists specifically to reason about retraining-vs-leakage, so a future caller skipping the argument would silently lose the guard. | Consider making `train_years` a required parameter here (unlike the more general-purpose `evaluate_by_year`, where optional makes sense), so the leakage check can't be accidentally omitted in this module. |
